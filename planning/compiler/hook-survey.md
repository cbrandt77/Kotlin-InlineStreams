This doc is to identify what parts of the compiler plugin infrastructure will allow us to do what we need.


# FIR Extension Points
FIR: where changes are visible to the IDE, but we don't have type info


- "Checkers" - Diagnostics
- "Expression Resolution" - add new implicit receivers
- "Assignment"
- "Delaration Generation"
  - Given an existing class, we need to know what members will be generated for it DURING THE SUPERTYPES STAGE.
  - Can also create top-level declarations, including classes
- "Function Call Refinement"
  - Unstable
  - Integrates with the "call resolution" mechanism: 
    - Resolution/completion of receiver
    - Resolution of arguments
    - Resolution of call itself
    - Resolution of outer call
    - Completion of call
    - Completion of outer call
  - Using this extension, the compiler plugin can generate local declarations into existing FIR source files. Given this injection, the
    * declarations fall under the constraints applied to FIR source files. One of these constraints is that the source elements of FIR
    * declarations must be distinct (see [KtSourceElement][org.jetbrains.kotlin.KtSourceElement]).
    *
    * All local declarations generated by this extension must have distinct source elements. The extension should create source elements with
    * a [PluginGenerated][org.jetbrains.kotlin.KtFakeSourceElementKind.PluginGenerated] fake source element kind. To avoid multiple local
    * declarations sharing the same source element, it is strongly recommended to use
    * [PluginGenerated.Custom][org.jetbrains.kotlin.KtFakeSourceElementKind.PluginGenerated.Custom] with a distinct marker per use case.
    * !!!!!! WE CAN GENERATE ARBITRARY FIR ELEMENTS!!! but can we add parameters to existing ones?
  - Allows a call to be completed with a more specific type than the declared return type of function
    - !!!!!!!!!!!
    - HOLY SHIT
    - WE CAN ACTUALLY
    - WE CAN MAKE THE `compile` FUNCTION RETURN A `(statements: List<KtStatement>, varDeclaration: VarSymbol)`!!!!!!
  - "Generated declarations should be local because this [FirExtension] works at body resolve stage and thus cannot create new top level declarations"
- "Function Type Kind"
  - Define family of similar functional types, like the stdlib "FunctionN"
  - Classes are synthetic
- "SAM conversion transformer"
- Status transformer
  - Could technically be used to transform FIR, but unstable if used this way
  - Modify declaration modifiers - access, modality, expect, actual, etc.
- Supertype generation
  - Given a class declaration, add supertypes to it
  - Also works on generated nested classes
- Type Attribute
- ~~Metadata Serializer~~
- FIR to IR REPL snippet configurator
  - Only works in the repl :(
